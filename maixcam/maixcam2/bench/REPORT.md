# SenseVoice 13 字标语评测报告

测试设备：MaixCAM2（maixcam2-ce3a，Ubuntu 22.04，2×Cortex-A53，约 955 MB RAM）

模型：`/root/models/sensevoice-maixcam2/`

测试语音：设备内置 MeloTTS 合成语音。不是真人麦克风录音，因此结果偏理想；
真实环境需要再用现场录音复测。

测试标语（13 字）：

```text
长春欢迎您来到吉林大学参观
```

字数：长1 春2 欢3 迎4 您5 来6 到7 吉8 林9 大10 学11 参12 观13。

## 1. 非流式识别结果

| 测试音频 | 识别结果 | CER | 说明 |
|---|---|---:|---|
| 正常语速 `slogan13.wav` | `长处欢迎您来到吉林大学参观。` | 7.69% | “长春”误成“长处” |
| 慢速 0.5× `slogan13_slow.wav` | `长春，欢迎您来到吉林大学参观。` | 0% | 完全正确 |
| 带标点 `slogan13_punct.wav` | `长春，欢迎你来到吉林大学参观。` | 7.69% | “您”误成“你” |

慢速音频重复 3 次均完全正确；带标点音频重复 3 次均只错“您/你”一个
字，说明识别结果稳定。

## 2. 词组检测

以 `长春`、`欢迎`、`吉林大学`、`参观` 作为四个词组：

| 模式 | 长春 | 欢迎 | 吉林大学 | 参观 | 词组命中 |
|---|---|---|---|---|---|
| 非流式正常 | 否 | 是 | 是 | 是 | 3/4 |
| 非流式慢速 | 是 | 是 | 是 | 是 | 4/4 |
| 非流式带标点 | 是 | 是 | 是 | 是 | 4/4 |
| 流式正常 | 否 | 是 | 是 | 否 | 2/4 |
| 流式慢速 | 否 | 是 | 是 | 是 | 3/4 |
| 流式带标点 | 否 | 是 | 是 | 是 | 3/4 |

当前业务只把 `长春` 注册为开门词组，其他三个词组只作为识别文本观察，
不会产生额外灯效事件。

正常语速下 `长春` 变成 `长处`，当前精确匹配 `keywords.json` 会判定不
开门。这是目前 13 字标语场景最直接的漏触发风险。

## 3. 延宕单字拆分

使用 `长——春` 慢速 TTS，流式 SenseVoice 最终结果：

```text
text = "长春"
timestamps(ms) = [60, 660]
```

即：

- “长”：约 60 ms
- “春”：约 660 ms
- 中间延宕约 600 ms

说明流式模型的 token timestamp 可以用来识别“单字被拉长”这一现象。

但当前 JLU_LEDLAB 主程序使用的是非流式 `refer()`，只拿到文本，没有
timestamp，因此现在会把“长——春”同样当作普通“长春”，无法拆分延宕
单字，也无法给“长”“春”分别产生独立事件。

单独截出的 `长.wav`、`春.wav`、`昂.wav` 在非流式模型中识别不稳定
（可能得到“好”“分”或空结果）。这说明 SenseVoice 适合句子级连续语音，
不适合直接替代一代的单字 KWS。

## 4. 时延

### 模型加载

- 服务启动 + 模型加载：约 **7～8 秒**。
- 首次推理冷启动：约 **5.2～5.5 秒**。
- 建议生产启动后先做一次静音/预热推理，避免第一句标语等待 5 秒。

### 非流式稳态推理

| 音频 | 中位时延 |
|---|---:|
| 13 字慢速（4.38s 音频） | 约 1.18s |
| 13 字带标点（约 3.2s 音频） | 约 0.97s |
| 13 字正常语速（2.90s 音频） | 约 0.90～0.94s |

当前主程序还使用 600ms 尾静音 VAD 和 100ms 分块，因此稳态下从人说完
到关键词判定，大约还要叠加 **0.7s VAD + 1.0s 左右 ASR**，即约
**1.7～1.9 秒**。

### 流式预录音频处理

以下是已录制音频一次性送入流式接口的处理时延，不是实时麦克风吞吐：

| 音频 | 音频长度 | 首个文本 | 最终文本 |
|---|---:|---:|---:|
| 13 字正常 | 2.90s | 0.615s | 1.214s |
| 13 字慢速 | 4.38s | 0.871s | 1.864s |
| 长——春 | 1.36s | 0.486s | 0.486s |

流式输出比实时快，但识别准确率明显低于非流式，不能直接拿最终流式文本
做精确开门判断。

## 5. 资源占用

模型加载后 SenseVoice 服务：

- RSS：约 **327 MB**
- 系统内存：约 201/955 MB 已用，约 684 MB 可用
- 模型加载/推理阶段 CPU 占用较高，使用 MaixCAM2 双核可以承受

## 6. 结论

### 可用部分

- 13 字中文标语在清楚、稍慢的语速下可以达到 **0% CER**。
- 正常语速/带标点约 **7.7% CER**，大部分词组能稳定识别。
- 流式 token timestamp 能区分“长——春”中约 600ms 的延宕。
- 句级词组（欢迎、吉林大学、参观）在慢速下完整保留。

### 当前不足

1. **精确词组匹配对 ASR 单字错误很敏感**  
   正常语速“长春”→“长处”会导致当前开门逻辑直接漏触发。

2. **当前主程序没有使用 timestamp**  
   无法区分普通“长春”和延宕“长——春”，无法把“长”“春”拆成两个
   独立控制事件。

3. **流式准确率低于非流式**  
   流式适合拿时间信息，不适合单独做最终文本判定。

4. **SenseVoice 不适合替代单字 KWS**  
   单独“长/春/昂”的短音频识别不稳定，一代 KWS 的单字优势仍然存在。

5. **当前没有通用词组表**  
   `keywords.json` 只有长春和长/春/昂字族，其他标语词组不会产生灯效。

## 7. 建议方案

建议采用混合链路，而不是只用 SenseVoice：

```text
麦克风
  ├─ 非流式 SenseVoice：最终文本/词组确认
  ├─ 流式 SenseVoice：token timestamp/延宕检测
  └─ RMS/能量包络：单字持续时间、起止点
        ↓
   拼音/模糊匹配 + 词组表 + 单字时长判定
        ↓
   STM32 PERFORM 事件
```

具体落地：

1. 增加一次模型预热推理。
2. 保留非流式 `refer()` 做最终文本判定。
3. 用流式接口的 `timestamps` 做词组边界和延宕检测。
4. 对“长春”增加拼音相似/编辑距离匹配，例如 `changchu` 与
   `changchun` 允许 1 个尾音差异，避免“长处/长出”漏触发。
5. 增加可配置词组表，而不是只写死“长春”。
6. 单字延宕用 timestamp 间隔 + 音频能量持续时间共同判断；不能只看
   一个 token 的时间戳。
7. 保留一代 KWS 作为单字/短词的高可靠触发通道，SenseVoice 负责长句
   和词组理解。
